# Keep个人副本：文件结构与活动映射 v1

状态：一份真实导出包的本地解密、结构读取、工作簿/FIT内部逐条匹配和基础归一化试运行通过；一条跑步的App截图8项基本信息对照通过，另与vivo样本确认一组跨源重复候选。自动同步与通用跨平台去重实现未验证。真实数量、日期、个人信息、轨迹链接与数值不进入本文或公开测试。

## 已观察的文件结构

- 外层AES ZIP包含运动记录工作簿、用户信息工作簿、一个装有FIT文件的内层ZIP。新版本不保证相同结构，应按签名和表结构识别。
- 活动表名为“运动记录”，另有空白工作表；用户信息表不是活动数据，本轮不读取账号属性值。
- 当前样本FIT可解码，含file_id/activity/sport/session，没有record或lap消息。因此不能宣称这些FIT有逐点GPS、逐秒心率或分圈。
- 跑步表中的“心率记录”为数字文本数组，存在空数组。当前未见元素自带时间戳，采样间隔未验证；不凭数组长度推定每秒采样。
- 当前跑步表“运动轨迹”为JPG图片引用，未跟随链接请求远端图片；这不等同于结构化GPS轨迹导出。归一化默认不输出这些URL。

## 活动表头和映射

映射库：`scripts/keep_activity_mapping.py`。依赖字段顺序与10个表头匹配，变化时拒绝静默映射。

| 表头 | 输出 | 处理 |
| --- | --- | --- |
| 运动类型 | sport、source_sport_label | 保留来源标签；当前“跑步/骑行/健身”分别映射running/cycling/training，未知不猜 |
| 运动时长(秒) | duration_s | 源报告时长，按秒保留，不用起止差覆盖 |
| 开始时间、结束时间 | start_time_utc、end_time_utc、wall_elapsed_s | 无时区时间必须显式指定来源时区，再转UTC；样本Excel/FIT对照观察到UTC+8，不作为所有用户默认 |
| 卡路里 | calories_kcal | 数字文本转数值；一条跑步已与App热量显示核对，其他类型不作推广 |
| 运动距离(米) | distance_m | 按表头米单位保留；健身零距离不伪造配速 |
| 平均心率、最大心率 | avg_hr_bpm、max_hr_bpm | 缺失/无效数不补零，不因有列名而宣称有实测值 |
| 心率记录 | 样本数量、可选samples | 默认只返回数量；明确请求时保留有效数值与缺失位置，不生成时间轴或固定频率 |
| 运动轨迹 | route_representation | 标注图片引用/未验证引用，不输出URL，不当作GPS点 |

计算配速使用报告用时÷距离公里数，字段为`calculated_pace_s_per_km`；原表没有独立的App显示配速字段，因此`reported_pace_s_per_km`保持空，不冒充实测显示值。

## 内部一致性检查与边界

真实样本的Excel活动与FIT session按开始时间和运动类型一一匹配，没有多候选；运动类型分布一致。可用的距离、心率与热量字段互证通过；少数时长存在不足1秒的精度差异。

FIT的`total_elapsed_time`在该样本中与`total_timer_time`相同，但往往不等于开始/结束时间差。需要分别保留源计时、FIT字段与墙钟经过时间，不能仅根据FIT字段名认定为实际墙钟时间，也不能把差值自动解释成停表。

上述工作簿/FIT互证属于内部一致性证据。随后取得的App截图另行完成了独立对照：距离、训练时长、总时长、热量、平均心率、按距离/训练时长计算并取整的配速、开始分钟、结束分钟，共8项通过。截图仅显示到分钟，不将文件中的秒数冒充截图证据。最大心率与心率序列尚未据此完成App对照。

同一记录与此前vivo样本的UTC起止时刻、距离、报告用时、热量、平均心率六项完全一致，应作为同一次运动的跨源重复候选，汇总时避免重复累计；保留两份来源关联，不删除原记录。本轮只是单组样本核对，尚未实现通用去重、冲突处理或批量合并。

两App的显示配速存在差异，不能以其中一个覆盖另一个。Keep导出表没有独立显示配速列，截图验证通过也不应回填为文件原生字段。截图另有运动负荷指标，当前导出表与FIT检查未确认可用对应字段，不能声称已导入该指标。
